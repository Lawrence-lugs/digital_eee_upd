How this maps to the exercise

Hardware you are building

feat_addr_gen walks each pixel’s patch. filt_addr_gen walks each filter. feeder_mp connects these addresses to the two spad_mp memories and aligns data with valid.

Input memory uses NCHW: image, input channel, row, column. Weight memory uses KCRS: filter, input channel, filter row, filter column. The rightmost coordinate moves fastest. Padding stays implicit.

A missing sample still consumes an entry. A raw read with valid=0 is ignored and becomes zero at the array edge. The supplied scratchpad reads every clock even when pop=0; this view highlights only requested reads.

What the demo supplies for you

The demo plays the testbench/controller role: it loads memory, starts groups of pixels and filters, and staggers lane requests. Extra groups run automatically when the work is larger than the array. It rewinds filters between pixel groups.

It uses the pipelined PE: input registers, a signed 16-bit product, and a signed 32-bit accumulator. Result readout is summarized as a “collect results” action; the output shift-register drain is not animated or included in the compute-clock count.

Play/pause freezes the entire demonstration. Independent lane stalls from the feeder unit test are deliberately excluded from this integrated schedule: they require additional coordination to keep operand pairs aligned.

Scope: dense cross-correlation, no filter flip, common stride and symmetric zero padding, no dilation, bias, activation, or quantization scaling. Open the original array simulator for the detailed array and output-drain view.
